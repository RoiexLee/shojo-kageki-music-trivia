# plan-009：整理新增音乐素材并扩充试听曲库

## 背景与目标

`music/` 已有 48 个按项目规范组织的歌曲目录，但根目录仍有一批带歌手后缀的 mp3/lrc 文件。需要把未重复收录的完整歌曲整理成 `music/<歌名>/<歌名>.mp3|.lrc|.jpg`，让工具链和前端能够使用；同歌名的重复文件保持原样。新增曲目并入共享曲库后，试听曲库继续按歌曲名字符串排序，编号在超过 100 首时使用三位数。

## 交付物清单

- [ ] 根目录中 73 组可用且 mp3/lrc 成对的歌曲移动到独立子目录，文件名改为目录同名。
- [ ] 从每个新增 mp3 的内嵌 mjpeg 封面提取同名 jpg；原有 48 个目录及根目录重复文件不改动。
- [ ] 将 73 首可用新增歌曲加入 `packages/shared/src/songs.json`，使索引与 `music/` 子目录逐一对应；元数据保留歌名和文件名中的演唱者，无法从文件名确认的字段使用项目允许的待补值。
- [ ] `apps/web/src/components/JukeboxStudio.tsx` 的试听曲目编号改为三位（`001`、`002`、……）。
- [ ] 补充实现纪要和实现评阅，记录素材整理、自测结果和未处理的孤立歌词。

## 涉及文件

- `music/`（新增歌曲目录及其 mp3/lrc/jpg）
- `packages/shared/src/songs.json`
- `apps/web/src/components/JukeboxStudio.tsx`
- `plans/plan-009-organize-music/implementation.md`
- `plans/plan-009-organize-music/implementation-review.md`

## 实现步骤

1. 读取现有 `songs.json` 与 `music/` 子目录，按最后一个 ` - ` 拆分根文件的歌名和演唱者。
2. 用 NFC/NFKC 与波浪线归一化判断重复歌名；已有目录对应的根文件保持原位。跳过无 mp3 配对的 `素敵なドレスを着させてよ` 孤立 lrc，以及歌词有效行不足 8 行的 `Fly Me to the Star #7`、`RE_`。
3. 为每个新增歌名建立目录，移动 mp3/lrc，并用 ffmpeg 从 mp3 的内嵌 mjpeg 流提取 jpg。
4. 生成唯一、符合 slug 规则的新增 id，并追加最小完整元数据；不重排既有题库数组，试听界面负责展示排序。
5. 将试听列表序号的 `padStart` 宽度改为 3。
6. 运行 `npm test` 与 `npm run build`；检查 songs.json 校验、目录对账和工作树差异。

## 验收标准

- [ ] `music/` 子目录数与 `songs.json` 条目数一致（预期 121），每个目录有同名 mp3/lrc/jpg。
- [ ] 根目录重复文件、歌词不足歌曲和孤立 lrc 未被移动或删除，并在实现纪要中记录。
- [ ] 新增 id 全部符合 `^[a-z0-9]+(-[a-z0-9]+)*$` 且不重复。
- [ ] 试听曲库仍按歌曲名排序，序号显示为 `001` 形式。
- [ ] `npm test` 与 `npm run build` 通过。

## 风险与回滚

- 文件移动与封面提取会产生大量新增文件；如需回滚，可按实现纪要中的新增歌名清单将目录移回 `music/` 根目录，并恢复 songs.json 与组件文件。
- 仅从音频内嵌封面提取 jpg，不校验封面内容；若某首封面不合适，可单独替换，不影响曲库契约。
- 演唱者、类型、出处等信息无法仅由文件名完整确认，新增条目先标记为“待补”，后续可再补充。
